# Сервер (museclass-server)

Проєкт Maven, пакет `ua.museclass`, код — у `server/`. Опис API для клієнта
(Android) — [`docs/api.md`](../api.md), звірений з кодом і живим dev-сервером
2026-10-06; змінив API — онови його. Запуск — у README всередині проєкту. Де й на чому він живе — у
[`hardware.md`](hardware.md).

**Структура (2026-10-05, Влад).** Точне дерево — у
[`server-layout.md`](server-layout.md). Коротко: корінь `server/` тримає лише
спільне — `pom.xml`, `src/`, `Dockerfile`, `dev/`, README з API. Код в одному
примірнику. Деплой окремо на машину, по 4 файли: `server/pc/` (робочий ПК,
Windows; веде чат про сервер; compose-проєкт `museclass-pc`, пам'ять 1g /
512MB) і `server/pi/` (малина й будь-який Linux; веде чат про малину). Обидва
`compose.yaml` збирають образ із кореня (`build: ..`). `mvn` запускається з
`server/`, `docker compose` — з `pc/` або `pi/`. Спільні файли правити окремим
комітом з позначкою «спільне».

Проміжна спроба зробити `server/pc/` повною копією коду прибрана звичайним
комітом; історію не переписували. Після перебудови `dev/sql_check.py` з
`server/` — 61/61, `docker compose config` в обох теках проходить.

**Історія коду.** `server/` у репо, з 2026-10-05 (закинуто з чату про малину, версія
2026-09-29 плюс шляхи під монорепо). Архіви `museclass-server.zip` більше не
актуальні. 2026-10-05 чат про сервер звірив зі своєю копією: Java-код, схема,
`pom.xml`, `backup.ps1` і `.gitattributes` збігаються байт у байт, деплой-файли в
репо новіші й повністю покривають його версію — нічого з чату про сервер не
загубилось.

## Що вміє
- **Акаунти:** реєстрація, вхід, JWT на 30 днів, профіль, інструменти (ті самі
  10 кодів, що в прототипі: piano, guitar, voice, violin, trumpet, flute,
  bass_guitar, drums, saxophone, bandura).
- **Класи:** коди `XXX-0X` (як `PNO-3A`), префікс викладач задає сам або
  випадковий. У випадковій частині немає I, O, 0, 1. Вступ за кодом прощає
  регістр, відсутній дефіс і кириличні двійники латиниці. Перевипуск коду,
  список учнів, виключення, вихід, перейменування, видалення. Код бачить тільки
  викладач.
- **Партитури:** завантаження `.musicxml` і `.mxl` (до 5 МБ). Сервер сам витягує
  назву, авторів, партії, кількість тактів і визначає інструмент партії (назва
  важливіша за MIDI-програму). Оригінал у `bytea`, віддається з ETag = SHA-256
  для офлайн-копій і 304. Нова версія з редактора — `PUT /scores/{id}/file`.
  Витягання партій сервер поки не вміє — див. [`open.md`](open.md).
- **Доступи:** одна SQL-функція `score_readable` — єдине джерело правди. Для
  чужого або недоступного — завжди 404, щоб не світити існування.
- **Авторські права** на двох рівнях: `public` тільки з
  `rights` ∈ {public_domain, folk} — і в сервісі, і check-обмеженням у БД.
- **Видача класу:** своя партитура або будь-яка публічна. Своя приватна при
  видачі автоматично стає класною.
- **Каталог:** пошук за назвою, композитором і аранжувальником (кирилиця без
  урахування регістру, `%` і `_` екрануються), фільтр за жанром, пагінація.
  Партитури з партією під інструмент користувача йдуть першими (`fits`).
- **Збережене і бібліотека:** «мої класи — усе видане», збережені.
- **Помилки:** `application/problem+json`, поле `detail` — готовий текст
  українською для показу користувачу.
- **Деплой:** multi-arch Dockerfile (amd64/arm64), compose з Postgres. API на
  `127.0.0.1:8080`, назовні тільки через `tailscale funnel --bg 8080`.
  `.gitattributes` тримає LF для Dockerfile, `.sh` і YAML.
- **Пам'ять:** за замовчуванням під Pi 4 на 2 ГБ: явний `-Xmx384m` для API
  (`API_HEAP`) і `shared_buffers=128MB` для Postgres (`PG_SHARED_BUFFERS`),
  піднімаються в `.env`. Явний `-Xmx`, а не відсоток: на Raspberry Pi OS ліміти
  пам'яті контейнерів можуть бути вимкнені в ядрі. Hikari — 8 з'єднань,
  віртуальні потоки ввімкнені.

Свідомо не зроблено: refresh-токени, скидання пароля, rate limit на вхід,
видалення акаунта, лічильник відтворень, PDF/MIDI-вкладення, видача окремим
учням.

## Перевірено
**Збірка (2026-10-06).** `.\mvnw.cmd verify` з `server/` на робочому ПК
(Windows 10, Temurin 21, Docker Desktop 29) пройшов з першого разу, `pom.xml`
не правився: Spring Boot 4.1.1, Testcontainers 2.0.5, 26 тестів (25 модульних
+ `ApiFlowTest` на `postgres:16-alpine`), jar зібрано, ~1,5 хв. Maven ставити
не треба — у `server/` є Maven Wrapper (Maven 3.9.16): `./mvnw` / `.\mvnw.cmd`.

**Помилки (2026-10-06).** Усі відповіді 4xx/5xx під `/api` — problem+json з
`detail` українською, і ті, що не з нашого коду: зламаний JSON, не-UUID,
неіснуючий шлях, 405/406/415, зламаний multipart (`ErrorHandler` успадковує
`ResponseEntityExceptionHandler`), 401/403 від Spring Security
(`SecurityProblems`, `WWW-Authenticate` лишається; окремі тексти для
відсутнього, зіпсованого й простроченого токена), непередбачене — 500.
Перевіряє `ApiFlowTest.everyErrorIsProblemJson`; `verify` — 27/27. Таблиця
текстів — у [`docs/api.md`](../api.md). Поза `/api` (і для збоїв до Spring
MVC, напр. у Tomcat) лишається стандартна сторінка Boot `/error`.

Схема й усі 40 SQL-запитів (рядки витягуються прямо з Java-коду) на
справжньому PostgreSQL 16 через prepared statements, 61 перевірка. Розбір
MusicXML — 25 модульних тестів плюс прогін по 377 реальних файлах з тестового
набору OpenSheetMusicDisplay (MuseScore, Finale, Sibelius, Dorico): усі
розбираються. На одному знайшлась і виправлена реальна проблема: заголовок
`encoding='UTF-16'` при UTF-8 вмісті. Захист від XXE і zip-бомби. Spring-код
компілюється із заглушками API. `compose.yaml` пройшов `docker compose config`
і з порожнім, і з заповненим `.env`, `backup.sh` — `sh -n`.

Інструменти цих перевірок — у [`server/dev/`](../../server/dev/README.md):
`sql_check.py` (61 перевірка SQL) і `RealFilesSmoke.java` (розбір реальних
файлів). 2026-10-05 обидва прогнані вже з репо: 61/61, 377/377. Новий запит у
репозиторії — перевірку в `sql_check.py` або в `ApiFlowTest`.

Як перевіряється: SQL — на живому Postgres, розбір MusicXML — на реальних
файлах, логіка HTTP — `ApiFlowTest` (потрібен Docker; піднімає свій Postgres
через Testcontainers, бойову базу не чіпає).

## Робочий ПК (2026-10-06)
**Бойовий** `museclass-pc` піднятий через `docker compose` з `server/pc/`:
API на `127.0.0.1:8080`, обидва контейнери healthy, `/actuator/health` — `UP`.
База створена 2026-10-06 о 20:02 з порожньої схеми (Flyway v1), тож даних у
ній немає, хіба що хтось зареєструвався через Funnel. Порт бази на хост не
виставлений, дивитися — `docker exec -it museclass-pc-db-1 psql -U museclass
-d museclass` (тільки читати).

О 20:10:01 бойовий зупинився штатно: спершу API, потім база (SIGTERM, код
143/0) — так робить `docker compose stop`. Зупинив Влад вручну, пробував, як
це працює — не збій. Політика
`unless-stopped` після такого сама не піднімає. Влад підняв вручну, після
цього знову healthy.

**Dev** за розділом «Розробка» з `server/pc/README.md` працює як написано:
`museclass-dev-db` (`postgres:16-alpine`) на `127.0.0.1:5433` (з 2026-10-06
тільки localhost, раніше слухала `0.0.0.0`), `.\mvnw.cmd spring-boot:run`
з `DB_URL`/`JWT_SECRET`/`SERVER_PORT=8081`, старт ~5 с, health `UP`, бойовий
не зачіпає. Дивитися — будь-яким GUI на `localhost:5433`,
`museclass`/`museclass`.

**Тестові дані dev** — `python server/dev/seed_dev.py` (опис у
`server/dev/README.md`): викладач `teacher@dev.museclass` / `teacher-dev-1`,
учень `student@dev.museclass` / `student-dev-1` (trumpet, guitar), клас «Dev:
оркестр» `DEV-..`, видані 4 демо з прототипу — бенд на 7 партій, «Щедрик»,
«Ода» (обидві публічні), «Етюд». Через API, повторно не дублює, на 8080 і
Funnel відмовляється. Партитури — `server/dev/seed/*.musicxml`, згенеровані
`export-demos.js` з `toMusicXML()` прототипу. Прогнано на dev: усе видано,
інструменти партій бенду впізнано, крім тромбона (`null`, коду для нього
немає).

Другий `spring-boot:run`, поки 8081 зайнятий, падає
з `BUILD FAILURE` після ~8 с — це не поломка, а зайнятий порт.

**Бекап (2026-10-07).** `backup.ps1` перевірено на dev-базі повним колом:
дамп (`-Fc`, 26 КБ) → `museclass-dev-db` пересоздано (0 таблиць) →
`pg_restore --clean --if-exists` → відбиток бази збігся до байта (2
користувачі, клас `DEV-6K`, 4 партитури, 13 партій, видачі, збережене, md5
файлів партитур, Flyway v1, `score_readable` і check-обмеження) → dev-сервер
стартував без міграцій, `seed_dev.py` увійшов тими ж паролями й побачив усе як
«вже була». Запуск через `powershell.exe -File` (як із Планувальника) і шлях
з помилкою теж перевірено. Бойову базу не чіпали.

Що полагоджено в скрипті й README: скрипт був жорстко прив'язаний до
`docker compose ... db` бойового — тепер `-Container` (порожньо = `db`
проєкту `museclass-pc`), `-OutDir`, `-Keep`; лог `backup.log` з `ok` /
`ПОМИЛКА` і код виходу 1 (раніше збій Планувальника ніде не було б видно);
перевірка, що дамп не порожній; у Планувальнику `-StartWhenAvailable` (ПК о
3:30 зазвичай спить, і бекап пропускався б); відновлення — окремим розділом
README із зупинкою `api` на час `pg_restore`.

## Не перевірено
Реальний клієнт проти бойового. `backup.ps1` без параметрів на бойовій базі,
команди Планувальника, відновлення бойової через `docker compose`, «Запуск на
Windows» з нуля.
